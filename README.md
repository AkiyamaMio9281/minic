# MiniC Compiler

MiniC is a small C-subset compiler written from scratch in C++17. It implements the complete pipeline from source text to execution without relying on Flex, Bison, LLVM, or an external assembler.

```text
MiniC source
    |
    v
  Lexer
    |
    v
  Parser -----> AST
    |
    v
Semantic analysis
    |
    v
Code generation
    |
    v
Stack-machine bytecode
    |
    v
Virtual machine
```

The project is intentionally compact enough to read end to end while still covering the major pieces of a real compiler: lexical analysis, recursive-descent parsing, semantic checks, name resolution, local-slot allocation, control-flow lowering, function calls, recursion, bytecode generation, and interpretation.

## Build

The provided build script targets Microsoft Visual C++ and automatically locates an installed Visual Studio C++ toolchain through `vswhere`.

Requirements:

- Windows
- Visual Studio Community, Professional, Enterprise, or Build Tools
- MSVC with C++17 support

Build with:

```bat
build.bat
```

The script compiles every `.cpp` file under `src\` and produces `minic.exe` in the repository root.

## Usage

```text
usage: minic [--tokens | --ast | --check | --bytecode | --run] <file.c>
  --tokens    print the token stream
  --ast       parse, then print the syntax tree
  --check     run semantic analysis, then print the resolved tree (default)
  --bytecode  compile and print stack-machine bytecode
  --run       compile and execute the program, then print main's result
```

For example:

```bat
minic.exe --run tests\gcd.c
```

prints:

```text
6
```

The default mode is `--check`.

### Token stream

```bat
minic.exe --tokens tests\gcd.c
```

Each token includes its source line, token type, and original spelling. Integer tokens also include their parsed value.

### Syntax tree

```bat
minic.exe --ast tests\gcd.c
```

This stops after parsing and prints the raw AST.

### Semantic analysis

```bat
minic.exe --check tests\gcd.c
```

Semantic analysis annotates the AST with information needed by code generation. Variables and declarations receive local-slot numbers, calls receive function indexes, and functions receive the maximum number of local slots required by their frames.

A fragment of the resolved tree looks like this:

```text
Program
  Function int gcd(a, b)  [locals 3]
    Block
      While
        Binary !=
          Var b  [slot 1]
          Int 0
```

### Bytecode

```bat
minic.exe --bytecode tests\gcd.c
```

This runs the front end and code generator, then prints the generated stack-machine instructions.

### Execution

```bat
minic.exe --run tests\gcd.c
```

This executes the full pipeline and runs the generated bytecode in the built-in VM. The value returned by `main` is printed to standard output.

## Supported MiniC Language

MiniC implements a deliberately small C-like language centered on integer computation, functions, recursion, branches, and loops.

### Types

- `int` is the only value type and is treated as a signed 32-bit integer.
- `void` is supported only as a function return type.

### Functions

Functions may:

- return `int` or `void`;
- take zero or more `int` parameters;
- call functions defined later in the file;
- recurse directly;
- recurse mutually with other functions.

Both of these forms mean "no parameters":

```c
int f() {
    return 0;
}

int g(void) {
    return 0;
}
```

Every program must define:

```c
int main() {
    ...
}
```

`main` must return `int` and take no parameters.

### Variables and scopes

Variables are local to functions. Nested blocks introduce nested scopes, and an inner declaration may shadow a declaration from an outer scope.

```c
int main() {
    int x = 1;

    {
        int x = 2;
        x = x + 1;
    }

    return x;
}
```

Parameters and the outermost function body share the same scope, matching C behavior.

Local variables are assigned integer frame slots during semantic analysis. Slots from disjoint sibling blocks may be reused, so a function's `localCount` is the peak number of simultaneously needed slots rather than the total number of declarations in the source.

### Statements

MiniC supports:

- local variable declarations;
- expression statements;
- empty statements;
- blocks;
- `if` / `else`;
- `while`;
- `return`.

Declarations are not statements. For example, this is rejected:

```c
if (x)
    int y;
```

Use a block instead:

```c
if (x) {
    int y;
}
```

### Expressions

Supported operators, from lower to higher precedence, are:

```text
=
||
&&
== !=
< <= > >=
+ -
* / %
unary - !
```

Assignment is an expression and is right-associative:

```c
a = b = 0;
```

is parsed as:

```c
a = (b = 0);
```

Logical `&&` and `||` use short-circuit evaluation.

### Grammar

The parser is a hand-written recursive-descent parser. Its core grammar is:

```text
program     = function*
function    = ("int" | "void") IDENT "(" params ")" block
params      = epsilon | "void" | "int" IDENT ("," "int" IDENT)*
block       = "{" block_item* "}"
block_item  = declaration | statement
declaration = "int" IDENT ("=" expr)? ";"
statement   = "if" "(" expr ")" statement ("else" statement)?
            | "while" "(" expr ")" statement
            | "return" expr? ";"
            | block
            | expr? ";"

expr        = assign
assign      = or ("=" assign)?
or          = and ("||" and)*
and         = equality ("&&" equality)*
equality    = relational (("==" | "!=") relational)*
relational  = additive (("<" | "<=" | ">" | ">=") additive)*
additive    = term (("+" | "-") term)*
term        = unary (("*" | "/" | "%") unary)*
unary       = ("-" | "!") unary | primary
primary     = INTEGER | IDENT | IDENT "(" args? ")" | "(" expr ")"
args        = expr ("," expr)*
```

Each grammar level maps directly to a parser function in `src/parser.cpp`.

## Semantic Checks

After parsing, the semantic analyzer performs a separate tree walk. It rejects programs that violate rules the grammar alone cannot express.

The checks include:

- a missing `main` function;
- `main` returning `void`;
- parameters on `main`;
- use of an undeclared variable;
- duplicate declarations in the same scope;
- a parameter redeclared in the function body's outermost scope;
- a variable used in its own initializer;
- a variable with the same name as a function;
- duplicate function definitions;
- calls to nonexistent functions;
- attempts to call a variable;
- incorrect argument counts;
- use of a `void` function result inside an expression;
- `return;` in an `int` function;
- `return value;` in a `void` function.

Functions are collected before any function body is analyzed. This allows forward calls and mutual recursion without function prototypes.

## Bytecode

Code generation consumes the annotations produced by semantic analysis instead of performing name lookup again.

The bytecode is designed for a simple operand-stack machine. Its instructions cover:

- integer constants;
- local loads and stores;
- stack duplication and removal;
- integer arithmetic;
- integer comparisons;
- logical negation;
- unconditional and conditional jumps;
- function calls;
- value and `void` returns.

Assignments preserve their value on the operand stack, which allows assignment expressions such as:

```c
int x;
int y;
x = y = 3;
```

Branches, loops, and short-circuit operators are lowered to jumps. Jump destinations are patched after the relevant bytecode regions have been emitted.

## Virtual Machine

The interpreter uses two main runtime structures:

- an operand stack for expression values;
- a call stack containing function frames.

Each call frame stores:

- the current function;
- its instruction pointer;
- its local-variable slots;
- the operand-stack depth at function entry.

Function arguments are evaluated from left to right. `CALL` creates a new frame and places the arguments into parameter slots `0..n-1`.

When a function returns, the VM discards temporary operand-stack values belonging to the callee and leaves only the function's return value for the caller.

The VM supports direct recursion and mutual recursion naturally through its call stack.

## Runtime Integer Behavior

MiniC uses signed 32-bit integers. The VM detects arithmetic situations that would otherwise rely on undefined signed-overflow behavior in C++.

Runtime errors are reported for:

- division by zero;
- remainder by zero;
- signed division overflow;
- negation overflow;
- addition overflow;
- subtraction overflow;
- multiplication overflow.

Falling off the end of `main` returns `0`, following C's special rule for `main`. Falling off the end of a `void` function behaves like `return;`. If execution reaches the end of any other `int` function without returning a value, the VM reports a runtime error.

## Errors

Compiler errors are printed to standard error in this form:

```text
<phase> error: line <line>: <message>
```

For example:

```text
syntax error: line 2: expected ';' after variable declaration, found 'return'
```

The compiler exits with status `1` for source-program errors and status `2` for invalid command-line usage.

## Intentional Limitations

MiniC does not currently support:

- arrays;
- pointers;
- `char`;
- strings;
- structures;
- global variables;
- `for` loops;
- function prototypes;
- multiple declarators such as `int a, b;`;
- bitwise operators;
- octal integer literals.

Several unsupported constructs are rejected explicitly rather than being silently interpreted differently from C. Examples include a lone `&` or `|`, malformed literals such as `123abc`, and integer literals with leading zeroes such as `010`.

Integer literals must not exceed `2147483647`. The minus sign is a unary operator rather than part of an integer token, so the minimum 32-bit value can be expressed as:

```c
-2147483647 - 1
```

Parser nesting is limited to 256 recursive levels so malformed or adversarial input produces a syntax error instead of overflowing the native stack. The Windows build reserves a larger process stack because very long flat expression chains can still produce deep AST walks without counting as parser nesting.

## Tests

Build the compiler first, then run:

```bat
test.bat
```

The test runner executes every `tests\*.c` file and compares its combined output against the corresponding `.expected` file.

To regenerate expected outputs intentionally:

```bat
test.bat update
```

Review the resulting changes with `git diff` before committing them.

Test prefixes indicate their purpose:

| Prefix | Purpose |
| --- | --- |
| `ok_` | Valid programs checked through semantic analysis |
| `lex_` | Lexer errors |
| `syntax_` | Parser errors |
| `semantic_` | Semantic-analysis errors |
| `run_` | End-to-end compilation and VM execution |

The execution tests cover arithmetic, chained assignment, loops, recursion, short-circuit evaluation, `void` calls, function fallthrough behavior, and integer overflow. `tests/gcd.c` is the main example program.

## Design Goals

The project favors explicit, readable implementations over framework-heavy abstractions:

- the lexer is hand-written;
- the parser is hand-written;
- AST traversal uses explicit node kinds rather than generated visitors;
- semantic analysis resolves names once and stores the results on the AST;
- the backend targets a small custom instruction set;
- the VM is implemented in the same C++17 codebase;
- the build has no third-party runtime dependency.

That makes the repository useful as a compact reference implementation of a complete compiler pipeline rather than only a parser or front-end exercise.
